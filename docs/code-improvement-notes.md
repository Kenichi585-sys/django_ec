# コード改善メモ

現時点では学習と動作理解を優先し、以下の項目はすぐに変更しない。
修正する際は、変更前に現在の画面表示とフォーム検証の動作を確認する。

## 1. `OrderForm.Meta.widgets` と `cart.html` の重複整理

### 現状

- `product/forms.py` の `OrderForm.Meta.widgets` で、請求先項目の `placeholder` と Bootstrap の `form-control` クラスを定義している。
- `product/templates/product/cart.html` では、同じ請求先項目の `<input>` を直接記述し、`placeholder`、CSS クラス、入力値、エラー表示をテンプレート側で制御している。
- テンプレートが `{{ form.last_name }}` のように Django のウィジェットを自動描画していないため、現在の `Meta.widgets` は実際の購入画面にほぼ反映されていない。

### 問題

- 同じ表示設定がフォームとテンプレートの2か所にあり、どちらが実際に使われているのか分かりにくい。
- 将来片方だけを変更すると、設定と画面表示が食い違う可能性がある。

### 推奨方針

現在の手動HTMLを維持し、ほかのテンプレートから利用されていないことを確認したうえで、`OrderForm.Meta.widgets` を削除する。

### 理由

- 現在の購入画面はBootstrapの行・列、エラー時の `is-invalid`、入力値の再表示を細かく制御している。
- Djangoのウィジェット自動描画へ変更すると、現在のレイアウトと条件付きCSSを再構築する必要があり、修正範囲が大きくなる。
- 未使用設定を削除する方が小さく、画面を壊す危険が少ない。

### 修正時の確認項目

- 姓、名、ユーザー名、メールアドレス、住所の見た目が変わらない。
- 入力エラー時に、正しい入力値が残る。
- エラーのある入力欄に `is-invalid` が付き、メッセージが表示される。
- `OrderForm` の検証結果に変化がない。

## 2. 疑似決済の入力案内を明確にする

### 現状

- カード番号の下に `動作確認用: 4242424242424242（ハイフンなし）` と表示している。
- 有効期限の下に `動作確認用: 12/99` と表示している。

### 懸念

- 「動作確認用」だけでは、なぜその値を入力するのか分かりにくい。
- カード番号は16桁であるだけでなくLuhnチェックを通る必要があるため、単に「16桁で入力」とだけ表示すると、利用者がランダムな16桁を入力して検証に失敗する可能性がある。

### 推奨方針

実在するカード情報を入力しない注意書きを残し、次のように入力条件とテスト値の目的を明示する。

- カード番号: `16桁のテスト番号を入力してください（例: 4242424242424242）。`
- 有効期限: `MM/YY形式の将来年月を入力してください（例: 12/99）。`

完全に例示番号を消す場合は、利用者がLuhnチェックを通過できる別の案内手段が必要になる。

## 3. 入力エラー後のカード項目の再表示方針

### 現状

- `card_name` は `value="{{ form.card_name.value|default:'' }}"` により、入力エラー後も再表示される。
- `card_number` と `card_expiry` には `value`属性を設定していないため、入力エラー後は空欄になる。
- これはDBから読み戻しているのではなく、エラー付きの `OrderForm` をテンプレートへ返した際の表示方法の違いである。

### 判断

- カード番号と有効期限をエラー画面へ再表示しない現在の挙動は、機密性のあるカード情報を不用意にHTMLへ再出力しない安全寄りの設計として維持する。
- カード名義はカード番号より機密性が低いため、再表示されても直ちに不具合とはいえない。
- 画面上の一貫性を優先してカード名義も空欄にする案はあるが、再入力の手間とのトレードオフになるため、セキュリティ確認のフェーズで最終判断する。

### 修正時の確認項目

- 入力エラー後もカード番号と有効期限がHTMLの`value`へ出力されない。
- カード情報が `Order` モデルおよびDBへ保存されない。
- 姓、名、ユーザー名、メールアドレス、住所などの非カード項目は入力値を再表示する。

## 4. ローカルのカード自動入力警告と本番HTTPS設定

### 現状

- ローカル環境は `http://localhost:3000` で動作するため、ブラウザがカード入力欄を検出すると「安全な接続を使用していないため、お支払い方法の自動入力は無効」と警告する。
- カード情報をDBへ保存しないことと、ブラウザからサーバーまでの通信をHTTPSで暗号化することは別の問題である。
- `production.py` ではPostgreSQL接続に `ssl_require=True` を設定しているが、Web通信側のHTTPS強制やSecure Cookie関連の設定は明示していない。

### 説明方針

- ローカルでは実在するカード情報を使わず、テスト値だけを入力する。
- 本番公開時はHTTPSを使用する。
- 実際の決済機能では、自前のフォームでカード情報をサーバーへ送らず、Stripe Checkout / Elementsなどの決済事業者を利用してトークン化する。

### 本番設定の確認候補

Herokuなどのリバースプロキシ環境での挙動を確認したうえで、必要なら次を設定する。

- `SECURE_PROXY_SSL_HEADER`
- `SECURE_SSL_REDIRECT`
- `SESSION_COOKIE_SECURE`
- `CSRF_COOKIE_SECURE`
- HSTS関連設定

設定値を追加するだけで終わらせず、HTTPSへのリダイレクト、CSRF、ログイン・セッション、Herokuのプロキシヘッダーを本番相当環境で確認する。

## 5. 注文の二重送信対策

### 現状

- 注文成功後は商品一覧へリダイレクトするため、成功後のページ再読み込みによるPOST再送信は起きにくい。
- 「購入する」の素早い二重クリックや、通信の再試行に対する完全な重複防止は実装していない。
- CSRFトークンは外部サイトからの不正送信を防ぐもので、同じ正規フォームの二重送信は防がない。

### 対策案

1. 送信開始時にJavaScriptでボタンを無効化する。小さなUX改善だが、通信の再試行や意図的なPOSTは防げない。
2. 注文フォームに一度限りのトークンを付与し、DBの一意制約とトランザクションで同一トークンの注文を1件に限定する。サーバー側で保証できるが、モデル・マイグレーション・ビュー・テストの修正が必要になる。
3. 実決済を追加する場合は、Stripeなどの決済APIの冪等性キーも使用し、二重課金を防ぐ。

### 当面の判断

現在は疑似決済のポートフォリオであり、理解対象を広げすぎないため実装は保留する。面接では、現状のPOST/Redirect/GETでページ再読み込みによる再送信を避けていることと、実サービスではサーバー側の冪等性保証が必要になることを説明できるようにする。
